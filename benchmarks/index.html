How fast is Zeno?

Six programs, each written once in Zeno, C, Rust and Python, doing the same steps and printing the same thing. Every number here was measured, and every time counts only if the program printed exactly what the C program printed.

What this shows

  • With one owner for each value, Zeno is as fast as C and Rust on programs that make many objects, and sometimes faster: its pool hands out and takes back a block in a few instructions, where C calls malloc and free.
  • On arithmetic and lists it is close to C, and most of what is left is the overflow check on every +, which --release drops, as Rust's release builds do. Index checks stay, as they do in Rust.
  • Floating point is still about two times slower than C. Each planet is an object reached through a list, where C holds the five in one array, and each sqrt and division checks its argument.
  • The garbage collector costs. A collector has to look at what is still in use, again and again. Zeno's is now about two times slower than C on many small objects. That is why a program can choose.
  • Building text is slower than it should be: for ch in text still makes a list of the characters first.

Choose how memory is freed

A program says it once, in its zeno.package:

package server
memory owned

or for one build, zeno build --owned. Single values can be owned in a collector program, and unsafe { } blocks manage memory by hand, as in C. See Choosing how memory is freed.

Where it started

The first run, on the same machine, before this work. The collector kept every block in one table that it sorted on each collection; it now keeps blocks in pages and finds them through a hash table (decision 22.5). The build with no collector was made for a chip, with a fixed pool of memory, and could not build text this big.

Interpreted

At a tenth of the size, because the interpreters are far slower. zeno run walks the syntax tree; zeno run --vm runs bytecode. Both are made to be simple to read and to give exact error messages, not to be fast, and they are slower than Python, which has had thirty years of tuning: the bytecode one by one and a half to seven times, the tree walker by three to fifteen.

The programs

  • Function calls fib: The slow recursive Fibonacci of a number: millions of calls and additions.
  • A tight loop loop: Whole-number arithmetic in a while loop, a billion times round.
  • Sorting a list sort: A quicksort written in the program, over ten million made-up numbers.
  • Building text strings: Ten million numbers turned to text, joined, then read a character at a time.
  • Many small objects trees: The binary-trees test: make and drop millions of small trees.
  • Floating point nbody: Five planets moved ten million small steps, as in the benchmarks game.

They are in bench/, one file per language, with the script that runs them:

cargo build --release
python3 bench/run.py --size big --engines c,rust,zeno,zeno-release,zeno-owned

Measured on 2026-11-16: Intel(R) Xeon(R) Processor @ 2.10GHz, 4 cores, Linux. zeno 0.3.0 (main), cc 13.3.0 with -O2, rustc 1.97.0 with -C opt-level=3, Python 3.13.18. Wall-clock time of the whole program, start to finish.

The runner has closed 0 of 1 halves

Zeno of Elea said Achilles can never catch the tortoise: first he must cover half the distance, then half of what is left, without end. It suits a compiler that will always be almost finished. The bar at the top of each page works the same way.
