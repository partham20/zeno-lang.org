28 The Board

Zeno is for programs that run on a board: a microcontroller with pins that drive LEDs and relays, registers that control its peripherals, and a clock. This chapter is about the board module, which is how a program reaches them, and about the simulated board that lets the same program run on a computer.

28.1 Blink

The program Zeno was made for, written on the first day, before there was a compiler, is this:

from board import led
from time import sleep

while true {
    led.toggle()
    sleep(500 ms)
}

It never ends, as firmware does not. Run on a computer, it prints led on, led off, led on every half second, until Ctrl-C stops it. Compiled for a microcontroller, the same lines blink the LED.

28.2 The simulated board

A computer has no LED on pin 13, so zeno run gives the program a simulated board. It has 64 pins, all low to begin with, with the LED on pin 13, where an Arduino Uno has it. It prints a line each time a pin changes level, which is what a logic analyser clipped to the pin would show:

from board import led

print(led, led.is_on())
led.on()
led.on()
led.toggle()
print(led.is_on())
Pin(13) false
led on
led off
false

The second led.on() printed nothing, because the pin was already high and did not move.

28.3 Pins

led is the pin the LED is on, and pin(n) is the pin with that number. A pin can do four things:

Written Does
p.on(), p.off() drive it high or low
p.toggle() give it the other level
p.is_on() is it high? A bool
p.number which pin it is

Pin is a type, so a function can ask for one, and a pin can go in a list, a field or a Pin or none:

from board import pin
from time import sleep

function flash(light: Pin, times: int) {
    for turn in range(times) {
        light.toggle()
        sleep(10 ms)
    }
}

let lamps = [pin(2), pin(3)]
for lamp in lamps {
    flash(lamp, 2)
}
pin 2 on
pin 2 off
pin 3 on
pin 3 off

A pin the board does not have is a ValueError:

from board import pin
let relay = pin(99)
error: uncaught ValueError: this board has no pin 99. Its pins are 0 to 63
 --> main.zeno:2:13
  |
2 | let relay = pin(99)
  |             ^

A pin is not an int: if it were, on(count) would compile, and so would led + 1. It is not an object either, because an object lives in memory from the collector, and blinking an LED should not need one. A pin is a kind of its own to the checker, and a plain number in the compiled program, so it costs what an int costs. Units work the same way. (Decision 3.15.)

28.4 Inputs

A button, a switch or a sensor that says yes or no is a pin the program reads. input_pin(n) makes the pin with that number an input, and gives an InputPin:

Written Gives
input_pin(2, pull_up) an input that a pull-up holds high
input_pin(2, pull_down) an input that a pull-down holds low
input_pin(2) an input that nothing pulls
b.is_high(), b.is_low() the level the pin is at now
b.number which pin it is

A button usually joins its pin to ground when it is pressed, and a pull-up holds the pin high the rest of the time, so a press reads low:

from board import input_pin, pull_up, led

let button = input_pin(2, pull_up)
if button.is_low() {
    led.on()
}
print(button, button.is_high())
InputPin(2) true

On a computer nothing presses the button, so a pull-up reads high, a pull-down low, and a pin nothing pulls keeps the level it had. Making an input prints nothing: the simulated board prints what the program drives, and a pull is not driven.

An InputPin has no on and a Pin has no is_low, and each mistake is found before the program runs:

from board import input_pin, pull_up
let button = input_pin(2, pull_up)
button.on()
error: an InputPin is read and not driven, so it has no `on`. Read it with `is_high()` or `is_low()`. A pin the program drives is made with `pin( )`
 --> main.zeno:3:1
  |
3 | button.on()
  | ^

1 error found. Nothing was run.

An output is driven and an input is read, and a pin is one or the other, so they are two types and the checker keeps them apart, as Rust’s embedded-hal does. An input says is_high and is_low and not is_on, because with a pull-up a pressed button is low, and “on” would then mean two things. The pull is said where the pin is made, because that is where the hardware sets it, and pull_up and pull_down are values of the board module of the type Pull, so a function can take one. (Decision 45.)

The example examples/doorbell.zeno counts presses of a button and rings a bell for each.

28.5 Reading a voltage

Most of what a board measures arrives as a voltage: a potentiometer, a thermistor, a battery through two resistors. analog_pin(n) gives an AnalogPin, read by the board’s converter:

Written Gives
a.voltage() what the pin is at now, in V
a.count() the same as the converter counted it, an int
a.max_count the count that stands for the whole reference
a.number which pin it is

The voltage has its unit, so it is compared with a voltage and nothing else, and it makes other units (Numbers with Units):

from board import analog_pin, pin

let sensor = analog_pin(4)
print(sensor.voltage(), sensor.count())
pin(4).on()
let level = sensor.voltage()
print(level, level.mV, level < 1200 mV)
print(level / 330 ohm, sensor.count() / sensor.max_count)
0 V 0
pin 4 on
3.3 V 3300 mV false
0.01 A 1.0

On a computer nothing is wired to the pin: one that is low reads 0 V, and one that is high reads the whole reference, 3.3 V and a count of 4095, as a voltmeter on it would.

A bare 512 from a converter means nothing until one knows its bits and its reference, and those are the board’s. So the board says them once, and voltage() hands the program volts, which the checker then keeps from being compared with a bare number. The count is there too, with max_count, for a share of the scale or a lookup table. (Decision 47.)

The example examples/battery.zeno watches a battery through a divider and lights the LED when it is low.

28.6 A serial port

A serial port is how a board talks: to a terminal on a computer, to a GPS module, to a modem. serial(n, speed) opens the port with that number, at a speed in baud, and gives a Serial:

Written Does
s.write("hi\n") sends the bytes of the text, and no line end of its own
s.write_bytes(frame) sends a list[u8] as it is
s.read_byte() the next byte, waiting for it: a u8 or none
s.has_byte() has a byte come that has not been read? No waiting
s.number which port it is

read_byte gives none only when no byte can come any more. On a board that is never; on a computer it is the end of what was typed, because there every serial port is the terminal itself, as a serial monitor is. A program that must not wait asks has_byte first.

from board import serial

let port = serial(1, 115200 baud)
port.write("ready\n")
var byte = port.read_byte()
var line = ""
while byte is not none and byte != 10 {
    line = line + char(byte)
    byte = port.read_byte()
}
port.write(f"got {line}\n")
ready
got on

The speed has a unit for the reason sleep has one: serial(1, 9600) does not say which number is the port. Text and bytes are sent by two methods, as files.write and files.write_bytes are, so neither is a guess. Reading a byte waits, which is what a console or a modem wants, and has_byte is there for a loop that has other work. (Decision 46.)

The example examples/console.zeno is a small command line over a serial port that drives the LED.

28.7 The clock

sleep waits for a time with a unit, and now() reads a clock that only goes forward, in milliseconds, from a moment such as when the board was switched on (Numbers with Units). Only the difference of two readings means anything:

from time import sleep, now

let start = now()
sleep(50 ms)
let took = now() - start
print("took at least 50 ms:", took >= 50 ms)
took at least 50 ms: true

28.8 Registers

A microcontroller’s peripherals, its timers, serial ports and converters, are controlled through registers: words of memory at fixed addresses, given in the data sheet. register(u32, address) names one, with its size:

from board import register

let control = register(u32, 0x4000_4400)
let data = register(u8, 0x4000_440C)

unsafe {
    control.write(u32(control.read() | 1 << 0))
    data.write(0x41)
    print(control.read(), data.read())
}
register 0x40004400 = 0x00000001
register 0x4000440c = 0x41
1 65

A value written must fit the register: control.read() 1| is an int, as every sum of sized numbers is (Sized Numbers and Bits), so u32(...) puts it back, with a check.

Reading and writing a register must be inside unsafe { }, because a wrong address or a wrong bit can stop a chip, and Zeno cannot check either. The block marks the lines a reviewer should read twice:

from board import register
let data = register(u8, 0x4000_440C)
data.write(0x41)
error: writing a register goes inside `unsafe { }`. Zeno cannot check that it is right, so the block marks the lines where a mistake can damage memory
 --> main.zeno:3:1
  |
3 | data.write(0x41)
  | ^

1 error found. Nothing was run.

On the simulated board a register is a word that remembers what was written, and each write is printed. On a real board it is the real address. Unsafe Code is about unsafe and memory by hand.

28.9 A traffic light

This program from the examples folder is a traffic light on three pins, written as a state machine with an enum. Its times are short, so the whole run takes a fifth of a second:

examples/signal.zeno

# signal.zeno: a traffic light on three pins, written as a state machine.
#
#     zeno run examples/signal.zeno      run it on the simulated board
#     zeno build --firmware --no-collector examples/signal.zeno
#                                        the build for a microcontroller:
#                                        no setjmp, no garbage collector
#
# On a computer the board is simulated. A line such as `pin 2 on` is what
# a logic analyser clipped to that pin would show. The times are short so
# that the whole run takes a fifth of a second.

from board import pin, led
from time import sleep, now

enum Light {
    Red
    Green
    Amber
}

let red = pin(2)
let amber = pin(3)
let green = pin(4)

# Switch the lamps over: the old one off, then the new one on.
function show(light: Light) {
    match light {
        case Red {
            amber.off()
            red.on()
        }
        case Green {
            red.off()
            green.on()
        }
        case Amber {
            green.off()
            amber.on()
        }
    }
}

function after(light: Light) -> Light {
    match light {
        case Red { return Green }
        case Green { return Amber }
        case Amber { return Red }
    }
}

# How long each light stays. The unit is part of the type: a function
# that returned `40` here would not compile.
function hold(light: Light) -> ms {
    match light {
        case Red { return 40 ms }
        case Green { return 30 ms }
        case Amber { return 10 ms }
    }
}

let start = now()
var light = Red
for step in range(7) {
    show(light)
    led.toggle()                 # a heartbeat: the program is alive
    sleep(hold(light))
    light = after(light)
}

# Seven steps hold for 200 ms in all. `now` only ever goes forward.
print("took at least 200 ms:", now() - start >= 200 ms)
pin 2 on
led on
pin 2 off
pin 4 on
led off
pin 4 off
pin 3 on
led on
pin 3 off
pin 2 on
led off
pin 2 off
pin 4 on
led on
pin 4 off
pin 3 on
led off
pin 3 off
pin 2 on
led on
took at least 200 ms: true

28.10 A real board underneath

A compiled program meets the hardware in four C functions, and these, with the number of pins, are everything Zeno knows about a board:

zeno_board_write(pin, level)   drive a pin high or low
zeno_board_read(pin)           is the pin high?
zeno_board_sleep(seconds)      wait
zeno_board_now()               a clock that only goes forward, in ms

A program that reads a pin needs a fifth, zeno_board_input(pin, pull), which makes the pin an input with no pull (0), a pull-up (1) or a pull-down (2). A program with a serial port needs four more, and ZENO_SERIALS, the number of ports: zeno_board_serial_open, _write, _ready and _read. One that reads a voltage needs zeno_board_analog and zeno_board_analog_read, with the converter’s bits and reference. Only a program that uses them calls them, so a header with four still builds every other program.

The simulated board is these four, written for a computer. For a real microcontroller they are written once, over the vendor’s library, in a header, and the C compiler is told where it is. Firmware shows how, with a sketch for an STM32. The Zeno program does not change by a line.

Four functions is the smallest surface a port can have: a board is working the day those four are. The checks, such as a pin that does not exist or a wait below zero, are done once above them, for every board, so the four can be four lines each. (Decision 5.12.)

28.11 What the board does not have yet

A button can be read, but nothing waits for it: a program looks at the pin as often as it needs to. On a computer nothing can press it yet. Nor can a voltage be fed to a pin there. Interrupts, timers and PWM are not in the board module yet. Until they are, a program reaches them through their registers, at the addresses the data sheet gives. Appendix G lists these.

from board import led, pin, register. A pin is driven with on, off and toggle and asked with is_on; Pin is a type. input_pin(n, pull_up) gives an InputPin, read with is_high and is_low. analog_pin(n) gives an AnalogPin, whose voltage() is in volts. serial(n, 115200 baud) gives a Serial, which writes text and bytes and reads a byte at a time. sleep and now keep time with units. A register is read and written inside unsafe. zeno run simulates the board and prints each change; a compiled program sits on four C functions that a real board provides.

  1. Blink the LED in Morse code: SOS, with dots of 100 ms.

  2. Write a class Relay with a pin and a name, and methods close and open that print what they do.

  3. Change the traffic light so that green lasts twice as long as red, and add a pedestrian lamp on pin 5.

  4. Write a register without unsafe and read the message.

  5. Change the doorbell to ring twice for a press that lasts longer than half a second.
