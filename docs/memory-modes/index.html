Choosing how memory is freed

A Zeno program that makes lists, objects and text needs memory for them, and has to give it back. There are three ways to do that in Zeno, and a program chooses:

How memory is freed Like Where you choose it
collector a garbage collector frees whatever nothing can reach Python, Java, Go nothing to say: it is what a program gets
owned every list and object has one owner, and is freed on the line its owner ends. No collector Rust memory owned in zeno.package, or zeno build --owned
by hand you ask for memory with allocate and give it back with free C an unsafe { } block, for the lines that need it

They mix, at the sizes where mixing has a clear meaning:

  • The program, in zeno.package: memory owned or memory collector. This is the one most programs set.
  • One build, on the command line: --owned or --collector, over what the file says.
  • One value, in a collector program: owned class Packet or owned list[int] (docs/ownership.md). That value has one owner and is freed where its owner ends, and everything else is the collector's.
  • A few lines, anywhere: unsafe { } (docs/unsafe.md).

Why not one line at a time: a value is made on one line and used on many, and how it is freed has to go with the value. Decision 22.1 has the whole reasoning.

A program that says memory owned

zeno new server

and add a line to server/zeno.package:

package server
memory owned

Now, in that folder:

  • zeno build main.zeno builds with no collector. Each list and object is freed on the line its owner ends, as in Rust. The program asks the system for memory as it needs it, in pieces that double.
  • zeno check main.zeno and zeno run main.zeno check the program by the same rules, so a mistake about who owns what is found before the build. The words for it are in docs/one-owner.md: a parameter looks unless it says take, pop() takes an item out of a list, and so on.
  • zeno build --collector main.zeno builds it with the collector after all, for one build.

For a chip

--no-collector is the same rules with a pool and a text room of a fixed size, set when the program is built (docs/pool.md), so the program can never fail to get memory from a system that is not there. memory owned with --firmware means the same.

Command Collector Memory
zeno build yes from the system, freed by the collector
zeno build --owned no from the system, in pieces that grow
zeno build --no-collector no one array of a fixed size
zeno build --owned --firmware no one array of a fixed size

--release

zeno build --release --owned main.zeno

--release drops the overflow checks: +, - and * of whole numbers wrap round, as the processor does, instead of stopping the program with an OverflowError. Everything else is still checked (an index past the end, // by zero, u8(300)), and zeno run checks everything as it always did. It is what Rust's release builds do, for the same reason: the check costs a little on every step of a tight loop. Decision 22.3.

What it buys

On the benchmarks in bench/ (python3 bench/run.py --size big; the numbers and how they were taken are in bench/README.md), a program that makes many small objects runs about as fast as the same program in C when it is owned, because the pool hands out and takes back a block in a few instructions. With the collector the same program is about two times slower than C.

The files

  • src/package.rs: the memory line of zeno.package (Memory).
  • src/main.rs: how_built, which turns the options and the file into a kind of build, and package_memory.
  • src/runtime.c: the pool that grows and the chain of text rooms, marked ZENO_HEAP; the collector, under "Where blocks live".
  • src/emit_c.rs, src/emit_llvm.rs: Options { release, grows }.
  • src/ast.rs: walks_in_place, which lets a loop skip its copy.

Things to try

  1. Build examples/scheduler.zeno with --owned --memory and with --no-collector --memory. Compare the last two lines of the reports.
  2. Write var n = 9223372036854775807 and n += 1, and build it with and without --release. Then run it with zeno run.
  3. Put memory owned in a zeno.package beside a program that shares a list between two variables. What does zeno run say now?
  4. Time bench/trees.zeno built the three ways in the table above.
